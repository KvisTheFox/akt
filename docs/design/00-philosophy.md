# akt — философия языка

## 1. Зачем ещё один системный язык

akt не пытается «быть лучше всех». Он решает конкретный набор задач:

| Задача | Требование |
|---|---|
| ОС, драйверы, embedded | Детерминированная память, прямые указатели, C ABI |
| Игровые движки, графика, аудио | Предсказуемые кадры, арены, отсутствие пауз |
| Бэкенд, сеть, CLI | Быстрая сборка, нормальные модули, async |
| Скрипты и автоматизация | AOT-компиляция, кэш, запуск без ручной сборки |
| Интеграция с C | Простое подключение C-заголовков и библиотек |

Существующие языки закрывают часть этих задач, но каждый вносит
свою цену:

| Язык | Сильная сторона | Цена |
|---|---|---|
| C | Простота, ABI, экосистема | Нет модулей, нет generics, ручная память без помощи |
| C++ | Мощь, экосистема | Сложность, медленная сборка, неявная семантика |
| Rust | Безопасность памяти | Сложность владения, `'a`, медленная сборка |
| Zig | Простота, comptime | Нестабильность, слабая инкапсуляция |
| Go | Простота, GC | Паузы GC, слабый FFI, размер рантайма |
| D | Баланс | Сложный рантайм, GC по умолчанию |

**akt** выбирает другой компромисс:

- память **детерминирована**: регионы + refcount + manual;
- синтаксис **минимален**: без `->`, `::` (кроме вариантов enum и
  ассоциированных функций), `'a`, препроцессора и макросов;
- компилятор **на C11**: быстрый bootstrap, переносимость, малый размер;
- кодогенерация **в C11**: используется вся зрелость GCC/Clang/MSVC;
- сборка **katek**: декларативная, воспроизводимая, с нативными
  C-зависимостями из xrepo/vcpkg/Conan/CMake/pkg-config.

## 2. Принципы (по приоритету)

1. **Детерминизм.** Одинаковый вход → одинаковый выход. Это касается
   памяти, сборки, артефактов и диагностики.
2. **Явность.** Нет неявных копирований, приведений, аллокаций и
   вызовов деструкторов. Всё видно в коде.
3. **Простота ядра.** Ядро языка — минимум конструкций; всё остальное
   в `std` или в пакетах экосистемы.
4. **Скорость.** Быстрая компиляция, быстрый код, быстрая сборка.
5. **C-совместимость.** C-библиотеки — не «второй сорт», а
   первоклассные зависимости.
6. **Читаемость.** Код должен читаться сверху вниз без знания
   скрытых правил.
7. **Инструментальность.** Формат, линтер, LSP, отладчик, doc —
   часть языка, а не «потом прикрутим».

Если новая возможность нарушает приоритет 1–3, она не добавляется.
Если она нарушает 4–7, она добавляется только с измеримым выигрышем.

## 3. Чего в akt не будет

### 3.1. Сборщика мусора — ни в каком виде

Запрещены tracing GC, mark-and-sweep, copying, generational,
compacting, incremental, concurrent, stop-the-world, cycle collector,
Boehm GC, libgc, MPS и «умный refcount, который сам находит циклы».

Причины:

- GC даёт непредсказуемые паузы;
- GC требует рантайма и тянет мегабайты;
- GC несовместим с драйверами, embedded и realtime;
- GC скрывает стоимость памяти от программиста.

Память освобождается:

- при выходе из региона — O(1) на регион;
- при выходе из арены — O(1) на арену;
- при обнулении refcount `shared` — O(1) на объект;
- явно в `manual`-режиме (`free`, `close`, `defer`).

Если модели памяти не хватает — это ошибка дизайна программы, а не
повод добавить GC.

### 3.2. Аннотаций времени жизни (`'a`)

`'a`, `&'a mut T`, `impl<'a> Trait<'a>` не будет. Владение
проверяется на уровне **регионов** (функция, блок, итерация, арена),
а не отдельных ссылок. Это даёт большую часть безопасности Rust без
сложности borrow checker.

### 3.3. `unsafe` как режима «выключить проверки»

В akt нет `unsafe fn` / `unsafe { }`. Но есть **C-граница**:
вызов C-кода, сырые указатели и `manual` не проверяются так же
строго, как безопасный akt-код. Это сделано явно:

- `cinclude` / `cfn` / `cstruct` — объявления C-API;
- `*T` — сырые указатели;
- `manual` — ручное управление ресурсом.

Компилятор не притворяется, что C безопасен. Он требует, чтобы
переход через границу был виден в коде.

### 3.4. Макросов и препроцессора

Нет `#define`, `#include`, `#ifdef`, `macro_rules!`, `template<>`,
процедурных макросов и codegen-плагинов. Вместо них:

- generics;
- `const fn`;
- обычные функции;
- встроенные конструкции (`defer`, `switch`-выражение);
- `cinclude` — только для C-заголовков (FFI, не макросы).

### 3.5. Исключений и `try/catch`

Ошибки — это значения: `Option<T>` и `Result<T, E>`. Оператор `?`
пробрасывает `Result`, оператор `??` даёт значение по умолчанию для
`Option`. Никаких `throw`, `catch`, `longjmp`, `setjmp`.

### 3.6. Неявной семантики

- Копирование явное: `a = b` — копия, `a = ^b` — ссылка.
- Приведение явное: `x as f64`.
- `null` только для `*T` и `cstring`.
- Память всегда указана: `auto`, `arena`, `shared`, `weak`, `manual`.
- Нет truthiness: `if (x)` допустим только для `bool`.

### 3.7. Обязательного мусора в синтаксисе

Нет обязательных `;`, `void`, `->`, `::`, `@attributes`, `let`,
`impl` (методы можно объявлять прямо в `struct`).

## 4. Модель безопасности: честно

akt **не** обещает «полную безопасность памяти, как Rust». Он
обещает:

| Область | Гарантия |
|---|---|
| Регионы | Значение не переживёт регион; ошибка компиляции |
| `^T` | Ссылка не переживёт владельца; ошибка компиляции |
| `shared` | Циклы через `shared` запрещены структурно |
| `manual` | Предупреждение, если ресурс не освобождён |
| Границы массивов | Проверка индексов; unchecked — только явный `std.ptr` |
| Типы | Строгая проверка, без неявных приведений |
| C-граница | **Не проверяется**. Это явный, аудируемый boundary |
| Гонки данных | **Не проверяются**. `shared` делает атомарным только refcount |

Это осознанный компромисс: akt проще Rust, но не притворяется
Rust. Для кода, где важна доказанная безопасность, нужен Rust или
формальная верификация; для кода, где важны контроль, ABI и
предсказуемость, akt даёт больше, чем C.

## 5. Чем akt похож и не похож на другие языки

| Свойство | C | C++ | Rust | Zig | Go | akt |
|---|---|---|---|---|---|---|
| Ручная память | ✅ | ✅ | ❌ | ✅ | ❌ | ✅ (`manual`) |
| Автоматическая память | ❌ | RAII | ✅ | defer | GC | ✅ регионы |
| Без `'a` | ✅ | ✅ | ❌ | ✅ | ✅ | ✅ |
| Без GC | ✅ | ✅ | ✅ | ✅ | ❌ | ✅ |
| Компиляция в C | ❌ | ❌ | ❌ | ✅ | ❌ | ✅ |
| Generics | ❌ | ✅ | ✅ | ⚠️ | ✅ | ✅ |
| Модули без `.h` | ❌ | ⚠️ | ✅ | ✅ | ✅ | ✅ |
| C-интероп | — | ✅ | ✅ | ✅ | ⚠️ | ✅ |
| C-пакеты из xrepo/vcpkg/CMake | ⚠️ | ⚠️ | ⚠️ | ⚠️ | ❌ | ✅ |
| Скорость компиляции | ⚡ | 🐢 | 🐢 | ⚡ | ⚡ | ⚡⚡ |
| Скорость кода | ⚡ | ⚡ | ⚡ | ⚡ | ⚡ | ⚡ |

«⚡⚡» — цель, а не измеренный факт. Она достигается за счёт
отсутствия LLVM, нескольких дешёвых проходов и потоковой
кодогенерации.

## 6. Целевые области

| Область | Модули | Специфика |
|---|---|---|
| ОС | `std.mem`, `std.ptr`, `std.os` | `manual`, `arena` |
| Драйверы | `std.ptr`, `std.mem` | `manual`, C-ABI, `volatile` через C-привязки |
| Игровые движки | `akt-gfx` (пакет), `std.math` | `arena`, `shared` |
| Бэкенд | `std.http`, `std.db.*` | `async`, `shared` |
| UI | `akt-ui` (пакет) | `shared` для состояния |
| CLI | `std.cli`, `std.io` | `auto` |
| Скрипты | нужные модули std | AOT + кэш |
| Embedded | `std.mem` | `manual`, минимальный профиль без Tier 1 |
| Интеграция с C | `std.c` | `cinclude`, `cfn`, `clink` |

Различие между областями — только в подключаемых модулях и профиле
сборки, а не в диалектах языка.

## 7. Принцип «нет магии» на примерах

### 7.1. Копирование

```akt
// ❌ не будет: неясно, копия или move
auto x = big_struct
use(x)

// ✅ будет: явно
BigStruct x = big_struct      // копия
BigStruct y = ^big_struct     // ссылка
use(^x)                       // передаём ссылку
```

### 7.2. Приведение

```akt
// ❌ не будет: неявная потеря точности
i32 x = 3.14

// ✅ будет: явно
i32 x = 3.14 as i32
```

### 7.3. Null

```akt
// ❌ не будет: неявный null
User u = find_user(42)
u.name

// ✅ будет: явный Option
Option<User> u = find_user(42)
switch (u) {
    case Some(user): { println(user.name) }
    case None:       { println("not found") }
}
```

### 7.4. C-граница

```akt
// ❌ не будет: скрытый вызов C
auto s = "hello".to_c()

// ✅ будет: явно
cinclude <string.h>
usize n = c.strlen("hello")
```

## 8. Что делает akt уникальным

1. Детерминированная память без GC и `'a`: регионы + `shared` +
   `weak` + `manual` + `arena`.
2. Компиляция в C, но с явным управлением памятью в сгенерированном
   коде — программист на akt этого не пишет.
3. Компилятор на C — быстрый bootstrap и отсутствие цепочки
   «Rust компилирует Rust».
4. Единый доступ через `.`: `ptr.field`, `ref.method()`, без `->`.
5. Арены как объекты первого класса: `arena ar; i32 ar.x = 5`.
6. `manual` + `defer`: ручное создание, автоматическое освобождение.
7. `switch` с pattern matching как выражение.
8. Малое ядро: 40 зарезервированных слов, 3 словесных оператора,
   3 контекстных слова.
9. `katek` с content-hash, offline-сборкой и reproducible builds.
10. **C-библиотеки как зависимости первого класса**: xrepo, vcpkg,
    Conan, CMake `find_package`, pkg-config, system, vendored.
11. XMake — официальный backend и способ сборки toolchain.

---

## 9. Кому akt не подойдёт

- Тем, кто хочет GC и не думать о памяти → Go, Python, JS.
- Тем, кто хочет доказанную borrow-checker'ом безопасность → Rust.
- Тем, кто хочет C++-шаблоны и метапрограммирование → C++.
- Тем, кому нужна зрелая экосистема «прямо сейчас» → C++, Rust, Go.
- Тем, кто не готов читать документацию по модели памяти → Go, Python.

akt — для тех, кто хочет «как C, но с модулями, generics и
предсказуемой памятью», и готов за это платить явностью.

---

## 10. Итог

akt — это язык, который:

- **не** пытается быть Rust, C++ или Go;
- **не** обещает невозможного;
- **явно** управляет памятью;
- **быстро** компилируется и собирается;
- **просто** интегрируется с C;
- **честно** называет свои границы.

Главный принцип:

> Если можно сделать проще — делаем проще.
> Если проще нельзя — делаем явно.
> Если явно нельзя — не делаем вообще.
